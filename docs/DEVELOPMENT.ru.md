# Как разрабатывать Context Cards вместе с Codex

Этот документ — рабочая договорённость для владельца проекта. Короткие инструкции для агента находятся в [AGENTS.md](../AGENTS.md), текущее состояние — в [WORK.md](WORK.md), команды проверок — в [TESTING.md](TESTING.md).

## Что мы меняем в процессе

Разрабатываем небольшими законченными задачами. У каждой есть наблюдаемый результат и способ проверить его. Сохраняем результат коммитом; публичный релиз собирает несколько проверенных изменений. Обычная задача не означает разрешение менять соседние механики, устанавливать сборку в рабочий vault или публиковать обновление всем пользователям.

При этом простая правка не требует многоступенчатого согласования: если цель ясна, Codex выполняет её, проверяет и коммитит. Обсуждение вариантов нужно там, где действительно предстоит выбрать продуктовый сценарий, интерфейс или существенный компромисс.

## Как формулировать задачу

Достаточно четырёх вещей: желаемый результат, пример проблемы, ограничения и признак готовности. Не обязательно знать название файла или предлагать техническое решение. Формулировка «кнопка перекрывается панелью» полезнее догадки «поставь ей z-index 9999» — причину должен найти разработчик.

```text
Задача: при раскрытии Examples весь заголовок usage должен читаться.
Сейчас: в узкой панели он обрезается, скриншот приложен.
Ожидаю: текст переносится, поле остаётся редактируемым.
Не меняем: генерацию примеров, Anki и остальные поля.
Готово, когда: проверено в узкой и широкой панели,
правки сохраняются после переключения Edit/Preview.
Сделай и закоммить. Без релиза.
```

Для ошибки добавляй версию или SHA сборки, режим, модель/провайдер, шаги, ожидаемый и фактический результат. Если поведение нестабильное — частоту и несколько примеров. Убирай из скриншотов URL с кодами авторизации, токены и личный текст; для воспроизведения лучше короткий синтетический пример.

Для новой большой функции сначала полезен такой запрос:

```text
Хочу добавить [сценарий пользователя].
Сначала изучи текущую реализацию, выяви спорные решения,
предложи простой интерфейс и критерии готовности.
Код плагина пока не меняй. После выбора варианта начнём реализацию.
```

Если просишь «просто объясни» или «покажи варианты», это отдельная задача без реализации. Если просишь «исправь» или «реализуй», не нужно дополнительно разрешать каждую обычную правку.

## Один результат — один рабочий чат

Продолжай текущую задачу в том же чате, пока уточнения относятся к ней. Для отдельной функции, другого большого дефекта или проверки готового изменения удобнее новый чат. Не нужно создавать чат на каждую кнопку и не нужно хранить весь проект в одной бесконечной беседе.

Открывай проект Codex в корне репозитория плагина: там лежат `manifest.json`, `package.json` и `AGENTS.md`. Файл правил в другой папке может не загрузиться автоматически. Новому чату можно написать:

```text
Работаем над Context Cards. Прочитай AGENTS.md и docs/WORK.md,
проверь текущую ветку и Git status. Продолжи задачу [ссылка на файл].
Источник истины — текущий код и зафиксированные решения.
```

`AGENTS.md` — постоянные правила, а не полная память проекта и не технический запрет. Файл не заменяет тесты и CI. Изменённые инструкции надёжнее подхватывать в новой сессии проекта; в уже открытом чате попроси прочитать их явно. Правила обнаружения описаны в [документации Codex](https://learn.chatgpt.com/docs/agent-configuration/agents-md).

Для параллельной разработки нужны отдельные рабочие копии Git, например worktrees. Две ветки сами по себе не изолируют два чата, которые одновременно редактируют одну папку. Для одного разработчика достаточно одной активной задачи; отдельный чат с чтением кода можно использовать для дополнительного ревью.

## Среда разработки

Проект использует Node.js 22+ и npm. В текущей Windows-среде Node/npm запускаются через WSL; в другой среде выбираем доступный способ, а не копируем команды вслепую. Например, из PowerShell:

```powershell
wsl.exe --cd /mnt/c/path/to/context-cards --exec bash -lc 'npm run build'
```

Здесь `/mnt/c/path/to/context-cards` нужно заменить путём к настоящей рабочей копии в WSL. Команды и зависимости отдельных проверок перечислены в [TESTING.md](TESTING.md). Никакие настройки самого Codex, модели агента или разрешений ОС эти договорённости автоматически не меняют.

## Как проходит задача

1. **Разобраться.** Прочитать затронутый код, воспроизвести ошибку или уточнить сценарий. Для большой задачи записать критерии готовности и план.
2. **Выбрать решение.** Для неоднозначного UI сначала показать макет с основными состояниями. Если ты попросил согласование, реализация ждёт выбора. Для понятного дефекта отдельный макет не нужен.
3. **Сделать небольшой законченный шаг.** Например, «вход и восстановление сессии», затем «выбор моделей», затем «полный сценарий генерации». Каждый шаг имеет собственную проверку и коммит.
4. **Проверить и отревьюить.** Воспроизвести исходную проблему на исправленной версии, проверить существенные соседние сценарии и итоговый diff.
5. **Передать результат.** Сообщить, что изменилось, что проверено, чего не проверяли, SHA коммита и как посмотреть результат. Отдельно указать, установлена ли сборка и нужен ли перезапуск.

Для задачи на несколько сессий Codex создаёт `docs/tasks/<slug>.md`: цель, критерии, ограничения, решения с причинами, ход работы, результаты проверок и следующий шаг. В `WORK.md` остаются ссылка и краткий статус. Для переименования кнопки такой документ избыточен.

Важное продуктовое решение сохраняем с причиной: например, «одна vocabulary-заметка создаёт два упражнения, чтобы сохранить общий источник и не дублировать поля». Для значимого архитектурного решения можно завести отдельный документ в `docs/decisions/`; пустую коллекцию документов заранее не создаём.

## Что именно считать проверкой

| Проверка                            | Что она показывает                                                   | Чего она не доказывает                                    |
| ----------------------------------- | -------------------------------------------------------------------- | --------------------------------------------------------- |
| Unit/integration с имитацией модели | Контракты, валидацию, отмену, таймауты, сохранение, обработку ошибок | Что реальная модель даст хороший английский               |
| Браузерный стенд                    | Действия и отображение настоящей панели в контролируемых условиях    | Полную совместимость с текущей темой и плагинами Obsidian |
| Проверка в настоящем Obsidian       | Работу захвата, панели и интеграции в конкретной установленной среде | Работу на всех ОС и аккаунтах                             |
| Временная коллекция Anki            | Поля, шаблоны, поиск и повторный экспорт                             | Безопасность любого изменения пользовательской коллекции  |
| Сравнение настоящих LLM             | Качество ответов на определённой выборке, задержку и число запросов  | Универсальную точность модели                             |

Тесты должны проверять договорённость с пользователем и реальные отказы. Для ошибок полезна регрессия, воспроизводящая проблему. Не пишем тест на каждый пиксель и не называем высокий процент покрытия доказательством отсутствия ошибок. Пороги покрытия не снижаем ради удобного прохождения.

Для сложного UI проверяем не только красивый заполненный экран: узкую панель, пустой результат, загрузку, ошибку, отмену, редактирование, повторную попытку и длинный текст — по применимости. Скриншот помогает оценить расположение; клики и сохранение данных проверяются отдельно.

Настоящие книги, аккаунты и Anki не становятся тестовыми фикстурами. По умолчанию используем development vault, синтетический/публичный текст и временную коллекцию. Проверка, расходующая значимый облачный лимит, и запись в реальные данные должны входить в разрешённый объём задачи.

## Для промптов нужен отдельный цикл

Сначала определить слой проблемы. Ошибка разбора SSE — транспорт; её не исправляет более строгая просьба «верни JSON». Обрезанный заголовок — интерфейс; его не нужно компенсировать короткими определениями.

При изменении промпта, схемы, reasoning или валидации:

1. Зафиксировать baseline SHA, модель и настройки.
2. Определить выборку: обычные случаи, известные ошибки и отдельные случаи, по которым не подбирали промпт.
3. Сравнить baseline и candidate в сопоставимых условиях. Для повторных запусков сохранять разброс, а не выбирать лучший ответ.
4. Отдельно посчитать валидность структуры, правильность смысла/исправления, ложные срабатывания, регрессии, время и число запросов. Показывать дроби: например, 18/20, а не только проценты.
5. Решить по результатам, оставляем изменение или откатываем. Противоречивые результаты так и описывать.

Не менять эталон только ради улучшения candidate. Исправления эталонов нужно объяснять и применять к обеим версиям. Кэшированные ответы подходят для проверки неизменных запросов и локальной обработки; новый промпт требует нового запроса модели. Кэш и живые запросы учитываются отдельно, в сравнение скорости кэш не входит. Подробности и существующие инструменты — в [TESTING.md](TESTING.md).

## Коммиты, локальные сборки и релизы

| Событие          | Когда делать                                                                                                      |
| ---------------- | ----------------------------------------------------------------------------------------------------------------- |
| Коммит           | Каждое законченное логическое изменение после подходящей проверки                                                 |
| Push ветки       | В рамках разрешённого рабочего процесса; публикация исходников не равна выпуску плагина                           |
| Локальная сборка | Чтобы проверить текущий код; указывать SHA, версия manifest может оставаться прежней                              |
| Установка сборки | В development vault; в рабочий vault — когда это входит в задачу, с резервной копией runtime и сохранением данных |
| Релиз            | По отдельному запросу после проверки набора изменений или исправления срочной проблемы                            |

**По умолчанию при обычной разработке не меняем номер версии, не создаём тег и не публикуем Release.** Номер меняется один раз при подготовке выпуска. Если локальная сборка имеет ту же версию, что релиз, различаем их по SHA: «manifest 0.3.41, local build abc1234». Это помогает воспроизводить ошибки.

Для существенной функции или эксперимента используем отдельную ветку; обязательный PR для каждой мелкой правки пока не нужен. По мере появления других участников и конфликтующих задач стоит перейти к PR и обязательным проверкам перед слиянием.

Фраза «выпусти релиз с накопленными изменениями» разрешает подготовку и публикацию после проверок. Фраза «сделай коммит», «запушь» или «подготовь к релизу» сама по себе не означает «опубликуй». Повторное формальное согласование уже разрешённого выпуска не требуется. Порядок выпуска находится в [RELEASING.md](RELEASING.md).

Откат обычно делаем новым revert-коммитом: сначала определить плохие коммиты и желаемый результат, затем сохранить более поздние независимые исправления. Откат кода не откатывает автоматически записи Anki, миграции данных и авторизацию — для них нужен отдельный план восстановления.

## Как управлять процессом короткими сообщениями

| Что нужно            | Что написать                                                                                                     |
| -------------------- | ---------------------------------------------------------------------------------------------------------------- |
| Обсудить идею        | «Проанализируй сценарий и предложи варианты. Код пока не меняй»                                                  |
| Получить критерии    | «Разбей на небольшие этапы и опиши, как проверим каждый»                                                         |
| Реализовать          | «Сделай выбранный вариант, проверь и закоммить. Без релиза»                                                      |
| Проверить критически | «Отревьюй изменения от SHA X до SHA Y: найди регрессии, проблемы данных и пропущенные сценарии. Пока без правок» |
| Исправить найденное  | «Исправь подтверждённые проблемы, добавь подходящие регрессии»                                                   |
| Проверить руками     | «Собери и установи в [точный test vault], укажи SHA и дай короткий сценарий проверки»                            |
| Передать в новый чат | «Обнови WORK.md: состояние, решения, проверки, нерешённое и следующий шаг»                                       |
| Выпустить            | «Выпусти релиз с накопленными изменениями после проверок»                                                        |

В ручной проверке тебе полезнее оценивать пользовательский сценарий: понятно ли действие, сохраняются ли правки, получается ли хорошая карточка. Запуск технических проверок, анализ diff и фиксация коммитов остаются работой Codex. Для авторизации и других чувствительных действий агент может оставить конкретный ручной шаг.

Если ошибка повторяется, коротко выясняем, почему её не поймали, и добавляем одну подходящую защиту: тест, правило проверки, пример в оценке модели или понятное состояние интерфейса. Постоянное правило в `AGENTS.md` нужно для повторяющегося класса проблем. Так процесс растёт из реальных потребностей проекта.

Основные подходы согласуются с [рекомендациями Codex](https://learn.chatgpt.com/guides/best-practices): ясная цель и признак готовности, небольшие задачи, постоянные инструкции, проверка и ревью. Конкретные правила выше выбраны для этого плагина и нашей работы, а не являются обязательными требованиями OpenAI.
